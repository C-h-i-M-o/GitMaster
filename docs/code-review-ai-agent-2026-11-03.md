## 问题记录

### R1 · P1 · 排队中的文件写入在停止后仍会执行

- 位置：`crates/gitmaster-core/src/agent/tools/registry.rs:187`、`tools/files.rs:162`、`crates/gitmaster-core/src/git/coordinator.rs:425`。
- 原因：阻塞线程进入文件工具前检查一次取消状态，随后 `FileTools::execute` 等待互斥锁和仓库写队列；获得执行资格后直接调用 `perform`，没有再检查取消状态。文件工具本身没有接收取消令牌。
- 触发：同仓库读取或其他操作占用队列，Agent 的 `write_file` 等待；此时用户停止运行，再释放队列。
- 实证：使用临时 Git 仓库和真实 `Toolbox`，先持有协调器读取、启动文件写入、确认目标尚不存在、取消，再释放队列。工具仍成功返回，目标文件内容为“取消后仍写入”。临时复现测试通过意味着缺陷被复现，并非修复通过。
- 影响：尚未开始修改文件的排队操作，在用户停止后仍产生新写入；这不同于已经开始的 Git 写操作需要等待真实结果。
- 建议：将取消令牌传入文件执行器，在获取队列之后、开始产生副作用之前重新检查；保留已开始写入的真实结果，不把取消当作回滚。增加排队取消回归。
- 状态：**动态确认，未修复**。

### R2 · P2 · 切换聊天加载期间的持久事件可能暂时漏显示

- 位置：`src/hooks/useAgent.ts:56`、`:69`、`:98`。
- 触发时序：切换到正在运行的聊天，`load` 清空 `record`；后端读取旧快照后，新事件先抵达前端，而读取 Promise 尚未完成。
- 原因：`receive` 在 `record` 为空时返回原值，事件未进入待合并队列；随后 `load` 直接采用旧快照。
- 影响：界面暂时缺少刚产生的消息或工具事件，直到结束通知触发重读或用户重新选择聊天。后端已持久化事件，不属于磁盘历史丢失。
- 建议：按聊天 ID 缓存加载期间的事件，以 sequence 与读取快照合并；测试“读取快照—通知抵达—读取返回”的固定时序。
- 状态：**代码路径确认，未做真实 IPC 时序注入，未修复**。

### R3 · P2 · 输入草稿跨聊天沿用

- 位置：`src/hooks/useAgent.ts:36`、`:56`、`:183`、`:216`。
- 触发：在聊天 A 输入未发送内容，然后选择聊天 B。`draft` 是共享状态，选择聊天时没有保存到 A 或切换为 B 的草稿。
- 影响：旧输入出现在 B 的输入框，发送后被加入 B 的模型上下文；切换项目并选择匹配该项目的聊天时，也可能把原项目草稿发送到另一个项目的聊天。后端的项目匹配检查不能识别草稿来源。
- 建议：按聊天 ID 管理草稿；没有会话时单独管理新聊天草稿。切换后恢复对应草稿，避免直接清空导致未发送内容丢失。
- 状态：**代码路径确认，未修复**。

### R4 · P2 · 退出保护未覆盖 Agent 活动运行

- 位置：`src/hooks/useWorkbench.ts:362`、`:1581`、`src/hooks/useBottomPanel.ts:54`、`src-tauri/src/lib.rs:69`、`src-tauri/src/commands/agent.rs:80`。
- 原因：退出检查涵盖原有操作、编辑器、设置和终端，没有检查 Agent 的活动运行；窗口销毁后才执行 `cancel_all`，没有等待 Agent 运行落下终态的关闭屏障。
- 触发：没有其他退出阻拦条件时，在 Agent 等待模型或执行工具期间关闭最后一个窗口。
- 影响：退出流程可以打断会话收尾；在途操作可能需要重启后按“结果未知”恢复。现有代码不足以保证注释所说的“在途 Git 写正常收尾”。这里没有证据证明仓库一定损坏，不能作此断言。
- 建议：由后端提供全部活动运行的停止及排空接口，窗口销毁前等待受控收尾；对排队操作与已开始写入分别处理，并验证慢速 Git 操作中退出。
- 状态：**退出链路缺口确认，进程退出时的实际副作用未实机复现，未修复**。

### R5 · P2 · 每次追加事件重新读取并解析整个聊天

- 位置：`crates/gitmaster-core/src/agent/store.rs:257`、`:283`。
- 原因：`append` 持有存储锁后调用 `events`，完整读取及反序列化 JSONL，仅为取得下一 sequence 和完整尾部位置；单聊天允许达到 64 MiB。
- 影响：随着聊天和工具输出增加，连续追加的累计处理量趋于二次增长；全局存储锁也使其他聊天和设置读写一起等待。运行循环本身还会读取完整历史。
- 建议：首次打开时扫描校验，在锁保护下维护已验证的尾部位置与 sequence；异常或文件变化时再恢复扫描。保留同步落盘和中断尾部修复规则。
- 状态：**复杂度与锁范围确认，未做大历史耗时基准，不声称已测出具体卡顿时长，未修复**。

### R6 · P2 · 流式输出每片重复扫描和传输完整累积文本

- 位置：`crates/gitmaster-core/src/agent/runtime.rs:268`、`:539`、`src/hooks/useAgent.ts:115`。
- 原因：每个 delta 都扫描全部累积文本、复制字符串、复制运行快照并通过 IPC 发送；前端每片更新 state。没有批量合并或刷新节流。
- 影响：在长回答且分片很小时，扫描、复制和传输总量趋于二次增长，可能占用 CPU 和 UI 更新资源；Anthropic 文本块累积同样存在完整字符串重建。
- 建议：合并短时间窗口内的流片，限定 UI 刷新频率；安全检测保留跨片段边界处理，不能简单改成只检查单片。结束时仍校验和持久化完整结果。
- 状态：**代码路径和复杂度确认，未做长流性能基准，未修复**。

### R7 · P3 · 聊天标题的前后端长度限制不一致

- 位置：`src/components/AgentPanel.tsx:84`、`crates/gitmaster-core/src/agent/store.rs:323`。
- 触发：输入 121～200 个普通中文字符并保存标题；前端允许输入，后端只接受最多 120 个字符。
- 影响：用户在输入时没有对应约束提示，点击保存后才失败。含非 BMP 字符时还存在 UTF-16 长度与 Rust Unicode scalar 计数差异。
- 建议：统一长度规则，并在输入处显示同一规则的剩余字数或校验提示。
- 状态：**约束不一致确认，未修复**。
