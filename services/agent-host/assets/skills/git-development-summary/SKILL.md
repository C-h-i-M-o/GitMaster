# Git 开发总结

## 目标

把一个或多个提交还原成面向汇报的短文档。让读者快速理解“做了什么、为什么这样设计、代码如何流转、重点考虑了什么、有哪些已实现的兜底”，而不是阅读逐文件变更清单或大量代码。

## 输入

优先从用户消息和当前环境获取：

- 一个或多个完整或短格式提交 ID；
- 目标仓库路径。用户未提供时，先尝试当前工作目录；无法唯一定位仓库时再询问；
- 可选的报告路径、目标读者、开发文档或聊天记录位置。

不要要求用户重复提供当前对话、当前仓库或工具已经能够可靠取得的信息。

## 证据原则

按以下优先级判断事实：

1. 提交中的代码、配置、迁移和测试；
2. 与这些提交直接相关的开发文档；
3. Agent 开发聊天与项目记忆；
4. 基于命名或代码结构的推断。

低优先级信息不能覆盖高优先级事实。聊天、文档或记忆描述了计划，但提交中没有实现时，不要写成已完成。确需使用推断时，明确使用“从代码结构看”“推测”或“未能确认”。

只总结指定提交带来的变化。不要把工作区未提交修改、相邻历史提交或当前分支上的其他功能混入报告。

## 工作流程

### 1. 校验范围

- 使用只读命令确认仓库根目录和工作树状态，例如 `git rev-parse --show-toplevel`、`git status --short`。
- 对每个 ID 使用 `git cat-file -e <id>^{commit}` 或等价方式确认它是可解析的提交，再读取提交标题、时间、父提交和完整 SHA。
- 任一 ID 无效或不属于当前仓库时，停止对该 ID 的总结并报告准确错误；不要用相似 SHA 猜测替代。
- 记录工作区已有修改，但不要更改、暂存、清理或把它们计入提交总结。

### 2. 建立代码事实

对每个提交检查摘要、文件统计和实际补丁，优先使用：

- `git show --stat --summary <id>`；
- `git diff <id>^ <id> -- <相关路径>`，或其他能明确父子差异的只读命令；
- 对合并提交先识别父提交，再选择能反映该提交实际引入内容的比较方式，并在报告边界中说明口径。

阅读关键入口、核心实现、数据结构、调用方、测试和错误处理。不要仅凭提交信息或文件名概括功能。

多个提交可能是同一功能的连续修正。按最终实现状态把它们合并成 1～3 个功能主题，必要时说明“后续提交修正了……”，不要按提交逐条写流水账，也不要重复统计同一变更。

### 3. 补充开发上下文

围绕提交 SHA、关键文件、函数、功能名称检索：

- 当前对话及可访问的历史 Agent 开发对话；
- 仓库内被修改或直接相关的需求、spec、plan、todo、README、ADR 等文档；
- 可访问的项目记忆或既有决策记录。

只提取能解释需求来源、设计取舍、已知风险和验证结果的内容。若某类来源不可访问，继续基于现有证据完成报告，并在末尾用一句话说明证据边界；不要假装已经检查过。

### 4. 形成证据映射

在写作前，为每个功能主题快速整理：

| 汇报问题 | 应回答的内容                                       |
| -------- | -------------------------------------------------- |
| 做了什么 | 用户可感知能力、范围和最终结果                     |
| 如何设计 | 关键分层、数据来源、接口或状态策略                 |
| 如何流转 | 入口 → 核心处理 → 输出/副作用                      |
| 考虑什么 | 正确性、兼容性、性能、安全、并发或体验中的关键点   |
| 如何兜底 | 提交中实际存在的校验、降级、隔离、取消、回滚或测试 |

“重要问题点”和“防御兜底”可能相关，但不要重复：前者说明风险或约束，后者说明代码已经采取的措施。若没有看到明确兜底，写“指定提交中未见独立兜底措施”，不要把建议伪装成实现。

### 5. 生成短报告

默认用中文 Markdown，采用以下模板：

```markdown
# [功能/模块名称]开发总结

> 提交范围：`<sha1>`、`<sha2>`  
> 汇报结论：[一句话概括最终交付价值]

## 1. 功能优化

[1～2 段，先说用户或业务结果，再交代边界；这是唯一允许相对完整展开的部分。]

## 2. 设计思路

- [核心分层或数据来源]
- [最重要的设计取舍]

## 3. 核心代码流程

1. [入口] → [处理] → [输出]
2. [必要的第二条主流程]

## 4. 重要问题点

- [关键约束或风险，以及为什么重要]
- [兼容性/一致性/安全/性能等重点]

## 5. 防御与兜底措施

- [已经实现的校验、降级、隔离或恢复机制]
- [已经存在的测试或验证保护]

> 证据边界：[仅在上下文缺失、合并提交口径特殊或存在未验证项时添加。]
```

## 篇幅与表达

- 默认控制在约 700～1200 个中文字符；功能确实复杂或提交较多时可以略增，但仍以“一屏到两屏读完”为目标。
- 第一节突出整体功能和业务结果；其余各节通常 2～4 个要点，每个要点尽量不超过两句。
- 核心流程优先用一条箭头链路表示，只保留理解架构必需的入口、服务、数据层和输出。
- 不粘贴代码块、完整类型、完整接口响应或长文件清单。每个要点最多引用少量关键文件、函数或接口名。
- 使用汇报语言，不写调查过程、命令执行日志或逐提交 diff 复述。
- 合并重复内容；同一机制不要同时在三节中换句话重复。

## 输出前检查

交付前逐项确认：

- 五个规定章节全部存在，第一节最完整，其余保持简要；
- 每个“已实现”“已验证”“已兜底”的陈述都能在提交、测试、文档或可靠对话记录中找到依据；
- 报告反映多个提交合并后的最终状态，没有遗漏后续修正；
- 没有混入工作区未提交变化，也没有把待办或建议写成已完成；
- 无效提交、不可访问的聊天/记忆、未运行的测试和未验证的外部依赖均已如实说明；
- 如用户要求保存文件，在获得适用的文件写入授权后再写入指定路径；否则直接在对话中返回完整 Markdown。
